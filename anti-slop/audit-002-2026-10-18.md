# The Work site audit 002

Date: 2026-10-18

Scope: current deployed site at `https://thework.tw78.workers.dev`, current workspace source, homepage and story-page markup, accessibility state management, performance delivery, SEO metadata, and security response headers. This is a read-only audit. No website source files were changed.

## Design read

Reading this as: a mobile-heavy university newsroom and permanent student-publication archive, using a broadsheet-inspired editorial language, with ENERGY 2 / RHYTHM 2 / MOTION 2.

The site has a clear identity. Merriweather gives the publication a newspaper voice, the purple paper palette is memorable, the homepage has a real editorial composition rather than a generic marketing template, and the story route is unusually strong for sharing and search. The previous visual fixes are present in production: the homepage toolbar is compact, the dark action color is in use, the article and CSS assets match the workspace, and the server now returns a real 404 page for unknown paths.

## Findings

### 1. HIGH, R-32: Homepage section filters report the wrong selected state to assistive technology

Evidence: `index.html:122-129` gives each homepage section control `role="tab"` and `aria-selected`. `app.js:6544-6550` changes `aria-pressed` on click but never updates `aria-selected`.

Visual users see the active section change correctly, but a screen reader can continue to hear All Stories as selected after the reader chooses News, Opinion, or another section. The control also mixes two state models: `role="tab"` with `aria-selected`, and button-style `aria-pressed`.

Smallest useful correction: either make these ordinary filter buttons and use `aria-pressed` consistently, or implement a complete tab pattern with `aria-selected`, `aria-controls`, a related panel, and keyboard arrow behavior. The first option is probably the better fit because the content is re-rendered rather than switched between static tab panels.

One-line rule reason: R-32 requires the accessibility state exposed to assistive technology to match the visible state.

### 2. MEDIUM, R-19 and R-32: The featured carousel auto-advances without a visible pause control

Evidence: `app.js:2613-2631` defines the carousel state, `app.js:2716-2719` starts autoplay, and `app.js:2727-2733` advances it every configured interval. `twCarousel.paused` exists, but there is no user-facing pause button and no code path that sets it to true. `app.js:2621-2623` checks reduced motion, but `app.js:2716-2719` explicitly continues autoplay for reduced-motion users.

The carousel is visually polished and its thumbnail progress ring explains the timing, but a reader can lose a headline while reading. People who prefer reduced motion still get content changes every eight seconds, even though the visual transitions are disabled. The current implementation also gives assistive technology no explicit pause or live-update control.

Smallest useful correction: add a Pause or Play control, pause on focus and pointer interaction, and disable autoplay entirely when `prefers-reduced-motion: reduce` is active. Keep manual arrows, swipe, and thumbnail selection.

One-line rule reason: R-19 requires motion to guide attention without taking control away from the reader, and R-32 requires an operable control for an auto-changing interface.

### 3. MEDIUM, C-4: Article hero images are exposed as decorative images with no editor-managed alternative text

Evidence: `workers/prerender.js:305-311` emits the article hero with `alt=""`. The client story renderer at `app.js:2394` follows the same pattern. The body-image renderer can preserve markdown alt text and captions at `workers/prerender.js:252-266`, but the main article thumbnail has no equivalent field.

A screen reader user receives the headline, deck, and credits, but not the subject or purpose of the main image. For a student newsroom, the hero may be a reporting photograph, infographic, or visual evidence rather than decoration. Empty alt is safe only when the image is genuinely redundant.

Smallest useful correction: add an optional image description or caption field to the article editor and use it as the hero alt text. If the field is empty, keep `alt=""` rather than inventing a description, but make the missing field visible to editors as an accessibility reminder.

One-line rule reason: C-4 requires the interface and its content to remain resilient for people who do not receive the default visual presentation.

### 4. MEDIUM, performance: The public page ships the entire newsroom application to every reader

Evidence from the current workspace: `index.html` is 77,717 bytes and contains public views, all admin panels, forms, modals, and editor markup. `app.js` is 293,850 bytes raw, about 77,886 bytes gzip. `styles.css` is 136,839 bytes raw, about 29,245 bytes gzip. The public shell also loads Supabase JavaScript, Google Fonts, and Umami from external origins at `index.html:61-69`.

The site still loads acceptably as a static asset site, and images are handled thoughtfully with responsive variants. However, mobile readers on mixed networks pay for code and CSS for article editing, permissions, staff accounts, release forms, and other views they will never open. The hidden admin markup also increases the amount of DOM the browser must parse.

Smallest useful correction: split the admin experience into a separate `/admin` entry point, or lazy-load admin JavaScript and admin-only styles after editor sign-in. Keep the public story and archive path independent from the CMS bundle. Measure mobile LCP and total blocking time before and after.

One-line rule reason: the audience is mobile-heavy, so performance is part of editorial access rather than an optional optimization.

### 5. MEDIUM, performance: Production asset headers are not using the versioned cache policy present in the workspace

Evidence: live `HEAD` responses for `https://thework.tw78.workers.dev/styles.css?v=50` and `https://thework.tw78.workers.dev/app.js?v=80` return `Cache-Control: public, max-age=0, must-revalidate`. The current local `workers/prerender.js:919-921` instead contains a branch intended to return `public, max-age=31536000, immutable` when the `v` query parameter is present. The deployed index, CSS, and JS hashes match the local files, so the issue is the deployed Worker response policy, not stale asset contents.

The cache-buster strategy is correct in the HTML, but the production Worker is not yet giving versioned assets the full benefit of that strategy. Readers can still revalidate the public CSS and JavaScript on every navigation. This is especially relevant because the app bundle is large.

Smallest useful correction: deploy the current Worker change, then verify the live headers for both versioned assets. Keep `max-age=0, must-revalidate` for unversioned HTML and use immutable caching only for URLs whose version changes with the asset.

One-line rule reason: cache-busting is useful only when the deployed cache policy treats versioned assets as immutable.

### 6. LOW, security hardening: The strict CSP is still report-only for scripts, styles, images, connections, and frames

Evidence: live responses include an enforcing policy with `frame-ancestors`, `object-src`, `base-uri`, and `form-action`, plus a much broader `content-security-policy-report-only` header. The local rationale is documented at `workers/prerender.js:828-876`, and the report-only policy contains `frame-src 'none'` even though the archive reader uses an external flipbook iframe.

The current headers are a good baseline and the report-only approach avoids breaking the CMS before traffic is tested. It is not yet a complete content security policy, however. The current report-only policy will also produce expected violations when the flipbook reader opens, so those reports need to be separated from genuine violations before promotion.

Smallest useful correction: exercise the admin editor, uploads, sign-in, archive reader, and public pages with CSP reporting enabled. Update the allowlist for the real iframe provider and any required origins, then promote the validated directives to the enforcing policy.

One-line rule reason: a security control should be enforced only after its real application flows have been verified, not left permanently as a non-blocking observation.

## What is working well

- Root page returns HTTP 200 and includes the current `styles.css?v=50` and `app.js?v=80` assets.
- Unknown paths return HTTP 404 with the standalone archive-themed 404 document.
- `/sitemap.xml` returns HTTP 200 with published story URLs and cache headers.
- `/robots.txt` allows crawling and points to the sitemap.
- A sampled story page has a canonical URL, article-specific Open Graph tags, a JPEG social-card response through the image proxy, and both Organization and NewsArticle JSON-LD.
- The social-card image proxy returned HTTP 200, `image/jpeg`, and a long-lived cache header.
- Security response headers include HSTS, `X-Content-Type-Options`, `X-Frame-Options`, `Referrer-Policy`, `Permissions-Policy`, and a baseline CSP.
- Local verification passed: `node scripts/smoke-check.js`, `node --check app.js`, `node --check workers/prerender.js`, and CSS parsing with esbuild.

## Recommended order

1. Fix the stale `aria-selected` state for homepage filters.
2. Add carousel pause behavior and honor reduced motion by stopping autoplay.
3. Add editor-managed hero image descriptions.
4. Deploy and verify the versioned asset cache policy.
5. Split or lazy-load the admin bundle after measuring mobile performance.
6. Promote the validated CSP after testing the external reader and CMS flows.

## Verification limits

- The built-in browser did not allow a live viewport click-through in this session, so no claim is made about current pixel-level rendering at a specific device width.
- The audit used live HTTP responses, deployed HTML and metadata, local source inspection, local syntax and CSS checks, and the existing design direction.
- No source files were changed for this audit.
